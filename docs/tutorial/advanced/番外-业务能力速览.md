# 番外 · 业务能力速览（选修）

← [17 Plugin 扩展](./17-Plugin扩展.md) · 返回 → [教程首页](../README.md)

## 目标

把框架自带的**业务型 Feature** 过一遍：知道每个解决什么问题、怎么装、以及**它明确不解决什么**。这一章不要求全部动手，但要求你能在选型时说清楚边界。

前置：学完第 17 章（Plugin 扩展），因为下面每个能力都是通过 `FeatureSet::plugin` 装配的。

## 必做

### 1. 装一个验证码，感受 Feature 的装配方式

```rust
use phoenix::plugin::FeatureSet;
use phoenix_captcha::CaptchaFeature;

let feature = CaptchaFeature::new();   // GET /captcha，路由名 captcha.image
let captcha = feature.captcha();       // 留一个句柄给登录 handler
let features = FeatureSet::new().plugin(feature)?;
```

前端一行：`<CaptchaImage />`。登录 DTO 加一个 `captcha` 字段，用 `CaptchaProtected` 提取器包一层就完成一次性校验。

**必须同时挂 `RateLimit`**——验证码是低成本摩擦，不是安全边界。

### 2. 在笔记里回答三个选型问题

1. 你的应用需要**无 session 的客户端**（App / 第三方）过验证码吗？需要就用 store 流（`with_store`），否则 session 流更省事。
2. 你的通知需要**站内信**（可查询、可标已读）吗？需要就开 database 通道，否则只发邮件。
3. 你的部署是**多实例**吗？是的话，实时广播要接 Redis，加密传输的会话要么共享要么粘性路由。

## 讲解：五个能力，各自的边界

| 能力 | crate | 解决 | **不**解决 |
| --- | --- | --- | --- |
| 图形验证码 | `phoenix-captcha` | 纯 Rust SVG、一次一用、常数时间比较 | OCR / 打码平台；无障碍替代通道 |
| 通知 | `phoenix-notify` | 邮件 + 站内信双通道，可查未读 | 短信 / 推送渠道（自行实现 `Notifier` 通道） |
| 支付 | `phoenix-pay` | 微信 Native / 支付宝当面付、退款、对账 | 除 CNY 外的币种；发票、分账 |
| 实时 | `phoenix-http::Hub` + `phoenix-redis` | 频道广播、在线状态、跨实例复制 | **投递保证**（pub/sub 是 fire-and-forget） |
| 加密传输 | `phoenix-crypto` | TLS 之上的纵深防御，密钥不进 bundle | **对终端用户保密**（浏览器必须能解密） |

### 支付：三条不可省的规矩

1. **金额永远是整数分**（`Amount`）。业务代码里出现 `f64` 金额就是 bug。
2. **先验签再取数**。任何未通过验签的回调都不会产出事件——这条在框架里是硬约束，不是建议。
3. **对账要双向比**。「账单有我们没有」和「我们有账单没有」是两种完全不同的事故：前者是货没发或通知丢了，后者是白发货。只比一个方向等于没对账。

退款有自己的状态机（一笔订单可以有多笔部分退款），可退额 = 订单金额 − 所有**未失败**的退款，在途的也占额，所以重复提交不会超退。

### 实时：为什么定向发送按身份不按连接 id

`ConnectionId` 是**每个 Hub 自己的句柄**，在另一台实例上没有任何含义——「连接 7」在两台机器上是两个不相干的人。而一个用户经常在多台实例上有多条连接。所以跨实例定向用 `hub.send_to_key("user:42", …)`。

### 加密传输：先读这段边界

浏览器为了渲染**必须**能解密，所以这不是端到端加密，**无法对终端用户隐藏内容**。它买到的是：密钥每次会话现场协商、不进 JS bundle、客户端不可导出。它是 TLS **之上**的一层，不替代 HTTPS。

- [ ] 能说出支付的三条规矩，以及「对账为什么必须双向」
- [ ] 能说出加密传输**不**提供什么保证
